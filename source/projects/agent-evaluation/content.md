> 将 Agent 的多阶段决策过程转化为可查询、可回放、可评测的结构化轨迹，支撑版本回归与 Bad Case 定位。

**项目类型：** 工程实践 · Agent 可观测与评测  
**主要内容：** Trajectory Schema、离线回放、分层评测与错误归因

> 本页仅介绍可公开的问题背景、技术思路与个人工作，不包含企业内部数据、架构细节和业务指标。

## 问题

智能客服 Agent 的一次回答可能经过意图路由、Query Rewrite、知识检索、模型推理和工具调用等多个环节。普通日志主要面向程序调试，字段分散且缺少统一语义；只看最终答案，又无法判断错误是来自路由、召回、推理还是工具执行。

另一个挑战是版本比较。模型、Prompt、知识库和 Agent 工作流会同时变化，如果缺乏可追溯的轨迹和稳定的离线样本，很难判断一次升级究竟改善了哪些能力，又引入了哪些退化。

## 工作内容

### 统一 Trajectory Schema

设计 Trace 与 Span 两级结构，串联会话、轮次和节点调用关系。轨迹记录节点类型、输入输出摘要、模型与 Prompt 版本、检索和工具信息、耗时、Token、错误以及评测结果，使不同版本能够对齐、查询和回放。

在数据治理上同步考虑 PII 脱敏、权限控制、长文本引用、异步埋点、Schema 版本兼容和敏感工具参数过滤，避免可观测系统反过来影响主链路或扩大安全风险。

### 分层评测体系

Agent 评测不能只看最终答案。项目将质量拆分到多个层级：

- **理解与路由**：是否识别正确意图并进入合适的技能。
- **检索与忠实度**：是否召回关键证据，回答是否得到证据支持。
- **工具调用**：工具、参数和调用顺序是否正确。
- **任务结果**：用户目标是否完成，回复是否完整。
- **过程效率与安全**：步骤、重复调用、延迟、Token、越权和隐私风险。

自动评测中，将规则可验证项与 LLM-as-a-Judge 分离，并通过明确 Rubric、原子维度、人工金标校准和版本化 Judge 配置降低偏差。

### 回归与错误归因

围绕高频场景、关键技能和历史 Bad Case 建设离线回归集。新版本上线前对同一批样本执行回放，从最终失败沿轨迹定位到理解、知识、推理、工具或回复节点，并将确认后的新失败模式沉淀为后续回归样本。

## 个人工作

- 设计统一 Trajectory Schema 与关键字段语义。
- 建设离线回归评测集和跨版本对比流程。
- 拆解 Agent 过程指标并组合规则评测与 LLM 判断。
- 建立轨迹回放、Bad Case 聚类与错误归因流程。

## 能力沉淀

这项实践将线上问题、离线评测和后续优化连接成闭环：线上轨迹暴露真实失败，离线回放验证修改是否有效，稳定的过程指标帮助定位收益来源，也为进一步构造训练数据与 Agent-RL 奖励提供基础。
