> 将函数级翻译扩展到仓库级迁移，以结构化依赖、最小必要上下文和编译测试反馈处理跨文件代码转换。

**项目类型：** 工程实践 · Coding Agent  
**主要内容：** 依赖分析、迁移规划、上下文工程与编译测试反馈

> 本页仅介绍可公开的问题背景、技术思路与个人工作，不包含企业内部代码、架构细节和业务指标。

## 问题

真实 C 仓库中的类型、函数、宏、全局变量和构建配置分布在多个文件中。单函数翻译即使可以编译，也不代表仓库能够完成构建或保持行为一致；直接将全仓文本放入长上下文，则会带来噪声、截断、位置偏差和显著的推理成本。

仓库级迁移因此不仅是生成问题，更是一个包含**程序分析、任务规划、上下文工程、代码生成与自动验证**的长链路 Agent 任务。

## 工作流

```text
仓库扫描
   ↓
AST / 符号 / 构建信息提取
   ↓
依赖图构建与迁移顺序规划
   ↓
检索当前单元的最小必要上下文
   ↓
生成 Rust
   ↓
格式化 / 静态检查 / 编译 / 测试
   ↓
错误归类与定向修复
   ↓
仓库级构建和回归验证
```

### 依赖分析与迁移规划

围绕文件、模块、类型、函数、宏和全局变量提取结构关系，并将调用、引用、包含和构建依赖显式化。根据依赖关系安排迁移顺序；遇到循环依赖时识别强连通分量，通过联合迁移或先稳定接口再迭代实现的方式推进。

### 最小必要上下文

长窗口只能提供承载能力，不能替代依赖建模。针对当前迁移单元，优先检索直接依赖、接口定义和相关测试；上层模块使用摘要，关键符号保留原文，并根据编译错误动态补充上下文，从而减少无关代码干扰。

### 编译反馈与定向修复

格式化、静态检查、编译和测试被接入 Agent 工作流。系统解析错误码、文件位置、主要消息和相关代码范围，合并重复或级联错误，优先处理根因；随后检索受影响的符号与调用方，让模型输出局部补丁，并限制重复修复次数。

## 个人工作

- 解析代码结构与跨文件依赖，围绕迁移单元组织必要上下文。
- 根据依赖关系和模块边界规划迁移顺序。
- 将静态检查、编译与测试接入生成和修复闭环。
- 对编译错误进行结构化解析、根因归类和定向修复。

## 评价方式

仓库级迁移需要分层评价，不能只统计生成文件数量。关键维度包括函数和文件编译成功率、仓库构建结果、单元与集成测试、行为一致性、迁移覆盖率、`unsafe` 使用、人工修改量、总耗时以及平均修复轮数。

这些指标共同回答三个问题：生成的代码能否进入真实构建系统、行为是否仍然正确，以及整个迁移流程是否具有实际工程效率。
