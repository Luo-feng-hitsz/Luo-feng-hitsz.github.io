## 0. 最重要的结论

你的核心竞争力不是“做过几个 LLM 项目”，而是一条比较完整且少见的主线：

> **围绕复杂任务中的大模型可靠性，做过规则/RAG 增强、编译与测试反馈、Agent 工作流、轨迹观测与评测，以及基于 MCTS + GRPO 的强化学习优化。**

这条主线能同时对应 JD 中的三类工作：

1. **基座与后训练**：SFT、LoRA、GRPO、DAPO、PPO、verl；
2. **Agent-RL 与应用落地**：代码迁移 Agent、客服 Agent 轨迹、评测闭环；
3. **技术价值验证**：CA/CSR/UR、回归集、开放式评测、版本迭代。

但你还需要主动补齐四个短板：

1. 简历没有大规模 **Pretrain** 的直接项目经验；
2. 缺少真正的 **多模态训练** 实践；
3. 缺少电商搜索、推荐、广告等业务指标经验；
4. 简历没有完整的在线 **A/B 实验** 案例。

面试策略不是掩盖短板，而是：

- 先用“可验证、可观测、可优化”的统一主线建立优势；
- 对不具备的经历明确说“没有直接做过”；
- 随后给出你对完整技术方案、关键风险和迁移路径的理解。

## 2. 你的统一个人标签

建议统一表述为：

> **面向复杂任务的可靠 LLM Agent 与强化学习优化。**

三个支撑关键词：

- **可验证**：编译器、单元测试、规则、执行反馈；
- **可观测**：Trajectory Schema、链路追踪、回放与归因；
- **可优化**：RAG/反馈修复、MCTS、SFT、GRPO、离线评测与版本回归。

不要把自己介绍成三个割裂方向：代码翻译、Agent、强化学习。应说明它们解决的是同一问题：

> 大模型在复杂长链路任务中会产生不可控错误，需要结构化任务分解、可靠反馈、过程观测和训练优化。

## 3. 与岗位最匹配的三条证据

### 证据 A：你做过从 Prompt/RAG 到训练优化的递进路线

1. IRENE：规则 + BM25/RAG + 语义总结 + 编译反馈；
2. TRAVEL：MCTS 构造推理轨迹 + SFT 冷启动 + 双奖励 GRPO；
3. 小鹏：Agent 轨迹观测 + 自动评测 + 版本回归。

这说明你不只会单点调 Prompt，而是知道什么时候应该：

- 补上下文；
- 引入工具反馈；
- 构造数据；
- 做参数更新；
- 建评测闭环。

### 证据 B：你擅长有验证器的复杂任务

代码任务有天然验证器：

- 编译是否成功；
- 测试是否通过；
- 行为是否与源程序一致；
- 是否出现 `unsafe`。

这一经验可迁移到电商：

- 商品属性是否与知识库一致；
- 工具调用参数是否合法；
- 订单操作是否成功；
- 推荐约束是否满足；
- 价格、库存、权益是否真实。

### 证据 C：你覆盖研究与落地两端

- 研究侧：问题定义、MCTS、PRM/ORM、GRPO、消融实验；
- 工程侧：仓库级依赖、3w+ LOC、编译反馈、客服轨迹、回归评测。

这与 JD 的“深入技术本质并驱动业务落地”高度一致。

# 第二部分：自我介绍与动机

## 4. 90 秒自我介绍

建议版本：

> 面试官您好，我叫罗锋，目前是哈尔滨工业大学深圳校区计算机技术专业硕士，研究方向是大模型代码生成、Agent 和强化学习。
>
> 我的经历主要围绕一个问题展开：如何让大模型在复杂长链路任务中变得更可靠、可验证和可优化。研究方面，我以第一作者开展了两项 C-to-Rust 工作。第一项 IRENE 使用 AST 规则分析、RAG 和编译器反馈，在不训练模型的情况下提升翻译准确性和安全性；之后我进一步做了 TRAVEL，通过规则引导的 MCTS 构造高质量推理轨迹，再结合 SFT 和双奖励 GRPO，让 Qwen2.5-Coder-7B 在测试集上达到 71.07% 的计算正确率。
>
> 工程方面，我在华为和蚂蚁分别做过函数级与仓库级代码迁移，处理跨文件依赖、上下文组织、生成修复和编译反馈闭环；目前在小鹏负责智能客服 Agent 的轨迹体系和评测优化，已经构建统一 Trajectory Schema、回归评测集，并支撑版本回归和 Bad Case 定位。
>
> 我认为这些经验与岗位的 Agent-RL、模型后训练和业务落地很匹配。虽然我还没有直接负责大规模预训练或电商多模态项目，但我已经具备从数据和评测、模型训练到 Agent 系统落地的完整问题意识，也希望把可验证强化学习和 Agent 评测经验迁移到搜索、导购和客服等电商场景。

### 自我介绍中的边界

- 说“71.07%”时必须补充：**在哪个数据集、什么指标、什么模型**；
- 不要笼统说“性能接近闭源大模型”；应说“在 xCodeEval 的 CA 指标上接近 Claude Haiku 4.5”；

# 第三部分：简历风险与必须统一的数据口径

## 6. 面试前必须修正或统一

### 6.1 ASE 论文标题不一致

简历标题：

> Towards Reliable C-to-Rust Translation via Rule-Guided **Search** and Reinforcement Learning

公开版本标题：

> Towards Reliable C-to-Rust Translation with Rule-Guided **Reasoning** and Reinforcement Learning

建议：正式投递版本与公开论文完全一致。标题不一致容易让面试官怀疑版本管理或成果真实性。

### 6.2 “提升 32.23 pp”的基线必须说清楚

Qwen2.5-Coder-7B-Instruct：

- Instruction baseline CA：38.83%；
- TRAVEL CA：71.07%；
- 差值：32.24 pp，受表格四舍五入影响可写 32.23 pp。

但相对最强 prompting baseline IRENE：

- IRENE CA：51.84%；
- TRAVEL CA：71.07%；
- 差值：19.23 pp。

回答时不能把“相对原始模型的提升”说成“相对最强基线的提升”。

### 6.3 “接近 Claude Haiku 4.5”必须限定口径

在 xCodeEval：

- TRAVEL Qwen2.5-Coder-7B CA：71.07%；
- Claude Haiku 4.5 CA：74.37%。

但编译成功率分别约为 87.38% 与 95.34%，且论文表中还有表现显著更强的闭源模型。因此推荐表述：

> 在 xCodeEval 的计算正确率这一单项指标上，7B 模型达到 71.07%，接近 Claude Haiku 4.5 的 74.37%；这说明方法能显著缩小特定任务差距，但不代表模型整体能力相当。

### 6.4 TRAVEL 并非所有指标都超过 SFT

Qwen2.5-Coder-7B：

- SFT：CA 68.35%，CSR 87.77%；
- TRAVEL：CA 71.07%，CSR 87.38%。

RL 提升了语义正确率，但 CSR 小幅下降。面试官很可能用这一点检验你是否真正理解论文。

推荐回答：

> 双奖励 RL 鼓励模型生成语义更丰富、行为更正确的翻译，因此 CA 提升；但相对更保守的 SFT 输出，部分复杂生成会带来轻微编译风险，使 CSR 有小幅波动。我们的消融也观察到仅保留执行奖励时模型更偏向保守、可编译的输出。这是语义正确性与句法保守性之间的权衡。

### 6.5 小鹏 57 条回归集规模较小

不要说“覆盖了客服 Agent 全部能力”。建议说：

> 57 条是当前阶段的高价值种子回归集，重点覆盖生产高频链路、历史 Bad Case 和关键技能，不是统计意义上的完整评测集。后续需要通过分层采样、聚类去重、风险加权和线上失败回流持续扩展。

### 6.6 “3w+ LOC”要准备完整口径

必须能回答：

- 是输入规模、一次任务规模，还是成功迁移并验证的规模？
- 统计是否包含注释、头文件、生成代码？
- 最终编译通过多少 LOC？
- 测试覆盖到什么层次？
- 迁移耗时、token 成本、人工介入量是多少？

如果这些数据未统计，应诚实说明，不要临场编造。

# 第四部分：简历逐段深挖题

## 8. 小鹏：智能客服 Agent 轨迹体系与评测

### 8.1 一句话项目定义

> 将客服 Agent 原本不可观测的多阶段决策过程结构化为可查询、可回放、可评测的轨迹，并基于生产数据构建离线回归与开放能力探索闭环。

### 8.2 高概率问题：为什么需要 Trajectory Schema？日志不够吗？

回答要点：

- 普通日志面向程序调试，字段分散且缺少统一语义；
- Agent 错误可能跨越路由、改写、召回、推理、工具调用多个节点；
- 需要父子关系、输入输出、版本、耗时、token、错误、反馈等统一字段；
- Schema 让轨迹可以跨版本对齐、聚合分析和离线重放；
- 还能把线上失败转换成评测样本与训练数据。

### 8.3 推荐的 Schema 结构

面试中可画出以下层级：

```text
Trace
├── trace_id / session_id / user_id_hash
├── agent_version / prompt_version / model_version
├── start_time / end_time / status
├── business_context
└── Spans
    ├── request_router
    ├── query_rewrite
    ├── retrieval
    ├── llm_reasoning
    ├── tool_call
    └── response / feedback
```

每个 Span 建议包含：

- `span_id`、`parent_span_id`、`turn_id`；
- 节点类型、输入摘要、输出摘要；
- 模型与 Prompt 版本；
- 检索文档 ID、分数、知识版本；
- 工具名、参数、返回码、重试；
- latency、token、cost；
- error type、fallback；
- rule score、judge score、人工标签。

### 8.4 如何避免轨迹系统自身造成问题？

回答要点：

- PII 脱敏和权限控制；
- 对长文本采用摘要、采样或对象存储引用；
- 异步埋点，避免阻塞主链路；
- Schema 版本化与向后兼容；
- 明确采样率和丢失率；
- Prompt、模型、知识库必须可追溯；
- 工具参数中密码、token 等绝不能直接落盘。

### 8.5 Agent 评测为什么不能只看最终答案？

最终成功可能掩盖低效或危险过程，最终失败也可能只是工具偶发错误。应分层评估：

1. **路由**：意图识别、是否进入正确技能；
2. **Query Rewrite**：信息保真、歧义消解；
3. **检索**：Recall@K、MRR、nDCG、证据覆盖；
4. **回答**：正确性、完整性、风格；
5. **忠实度**：答案是否由证据支持；
6. **工具选择**：工具、参数、顺序是否正确；
7. **过程效率**：步数、重复调用、latency、token；
8. **任务结果**：用户目标是否完成；
9. **安全**：越权、隐私、错误操作。

### 8.6 LLM-as-a-Judge 有什么问题？

- 位置偏差、长度偏差、风格偏差；
- 自偏好或同源模型偏好；
- Prompt 敏感；
- 非确定性；
- 容易被被评文本中的指令注入；
- 与业务真实满意度不一定一致。

改进方法：

- 将规则可验证项与 LLM 判断分离；
- 明确 rubric，拆成原子维度；
- 使用 pairwise 而非模糊绝对打分；
- 多次采样或多 Judge；
- 用人工金标校准，报告一致性；
- 对 Judge 输入做隔离和转义；
- Judge Prompt、模型和温度必须版本化。

### 8.7 57 条评测集如何构建才有说服力？

推荐回答结构：

1. 来源：高频生产流量 + 历史 Bad Case + 核心技能；
2. 去重：语义聚类或意图分层，减少同质样本；
3. 分层：普通、边界、对抗、工具异常、多轮切换；
4. 标注：输入、预期路由、关键证据、允许答案、禁用行为；
5. 版本：样本不可静默修改，保留变更记录；
6. 扩展：新版本失败、线上差评、探索评测回流。

### 8.8 什么是开放式能力探索评测？

固定回归集只能回答“旧能力是否退化”，开放式探索要寻找未知边界：

- 自动生成多样用户目标；
- 修改条件、注入冲突信息和工具异常；
- 让探索 Agent 寻找能触发失败的输入；
- 对轨迹聚类，识别新的失败模式；
- 人工确认后沉淀为回归样本。

### 8.9 Bad Case 如何归因？

建议使用错误树：

```text
最终任务失败
├── 理解错误
│   ├── 意图路由错误
│   └── Query Rewrite 丢信息
├── 知识错误
│   ├── 未召回
│   ├── 召回错误
│   └── 知识过期
├── 推理错误
│   ├── 未使用证据
│   └── 多轮状态丢失
├── 工具错误
│   ├── 选错工具
│   ├── 参数错误
│   └── 工具执行失败
└── 回复错误
    ├── 内容不完整
    └── 表达或安全问题
```

### 8.10 如何从评测走向 Agent-RL？

可迁移路径：

1. Schema 收集轨迹；
2. 规则与 Judge 产生 step/trajectory reward；
3. 选择可重放、可验证的环境；
4. 构造 SFT 冷启动轨迹；
5. 多轮 rollout；
6. 用任务结果、过程质量、成本与安全组成奖励；
7. GRPO/PPO 优化；
8. 离线回归 + 影子流量 + 小流量 A/B。

## 9. 蚂蚁：仓库级 C-to-Rust 迁移 Agent

### 9.1 一句话项目定义

> 把函数级翻译升级为仓库级迁移：先解析代码和依赖，再按结构组织上下文与翻译顺序，并通过编译/测试反馈持续修复。

### 9.2 为什么函数级方法不能直接迁移仓库？

- 类型定义在其他文件；
- 宏、条件编译和头文件影响语义；
- 全局变量、共享状态与初始化顺序；
- 函数调用图与跨模块接口；
- C 与 Rust 模块系统、FFI、构建系统不同；
- 全仓文本直接塞入上下文成本高、噪声大、易截断；
- 单函数编译成功不代表仓库可构建或行为一致。

### 9.3 推荐工作流

```text
仓库扫描
  ↓
AST/符号/构建信息提取
  ↓
依赖图构建与 SCC 缩点
  ↓
按拓扑与模块边界规划迁移
  ↓
检索当前单元的最小必要上下文
  ↓
生成 Rust
  ↓
格式化 / 静态检查 / 编译 / 测试
  ↓
错误归类与定向修复
  ↓
接口一致性检查
  ↓
仓库级构建和回归验证
```

### 9.4 依赖图如何建？

节点可以是文件、模块、类型、函数、宏或全局变量；边可包括：

- `include`；
- 函数调用；
- 类型引用；
- 变量读写；
- 宏展开；
- 构建依赖；
- FFI 边界。

注意调用图通常有环。处理方式：

- Tarjan/Kosaraju 找强连通分量；
- 将 SCC 缩成 DAG；
- SCC 内联合迁移或先声明接口再迭代实现。

### 9.5 为什么 Long Context 不能替代依赖建模？

- 上下文长度足够不等于模型能有效利用远距离信息；
- 无关代码稀释注意力；
- 位置偏差与 lost-in-the-middle；
- 成本、TTFT、KV Cache 显著增加；
- 依赖关系需要明确结构和优先级；
- 仓库会超过任何固定窗口。

最合理的是：**结构化依赖检索 + 分层摘要 + 必要原文 + 编译反馈**。

### 9.6 编译错误如何进入修复闭环？

不要把全部编译日志原样回灌。应：

1. 解析 error code、文件、行号、主消息、相关 span；
2. 去除重复和级联错误；
3. 优先修复根因错误；
4. 检索相关符号定义与调用方；
5. 要求模型输出 patch，而不是全文件重写；
6. 限制最大重试次数；
7. 相同错误重复出现时切换策略或人工介入。

### 9.7 如何保证工作流可靠？

- 每一步产物持久化；
- 幂等任务和断点续跑；
- 输入、Prompt、模型、依赖图版本化；
- 生成结果缓存；
- 编译和测试放在沙箱；
- 超时、资源限制与危险系统调用隔离；
- 明确人工审批点；
- 记录每次修复前后的 diff 与验证结果。

### 9.8 如何评价仓库级迁移？

分层指标：

- 文件/函数编译成功率；
- 仓库 build success；
- 单测与集成测试通过率；
- 行为一致性；
- `unsafe` 样本率与 LOC 占比；
- API/ABI 兼容；
- 迁移覆盖率；
- 人工修改量；
- 总耗时与 token 成本；
- 首次成功率、平均修复轮数。

### 9.9 与 DepTrans 论文的区别要讲清楚

公开 DepTrans 包含 RAST 和 DGIR，并报告 85k 训练样本、145 个仓库级实例等。你的蚂蚁实习项目不应在没有证据时直接等同于论文系统。

面试时应明确：

- 哪些设计来自你的实习工作；
- 哪些属于你参与的论文；
- 哪些是团队已有基础设施；
- 论文方法和开源工作流的关系。

## 10. 华为：IRENE 规则增强 C-to-Rust

### 10.1 一句话项目定义

> 不更新模型参数，通过 AST 规则识别、类别内 BM25 检索、结构化语义总结和编译器反馈，提高 C-to-Rust 的正确性、可编译性和安全性。

### 10.2 三个核心模块

1. **Rule-Augmented Retrieval**：AST 分析输入代码，识别指针、I/O、混合类型、数组等规则类别，在同类别中检索示例；
2. **Structured Summarization**：先生成 `<Input, Output, Functionality>` 结构化摘要；
3. **Error-Driven Translation**：编译 Rust，解析错误并迭代修复。

### 10.3 为什么先按规则类别过滤，再做 BM25？

- 纯文本相似不等于翻译难点相似；
- 同样包含 `malloc` 的代码更需要所有权/容器转换示例；
- 类别过滤提高规则相关性；
- BM25 再选择局部结构最相似的示例；
- 这是一种“符号规则约束召回空间 + 稀疏检索排序”的混合方法。

### 10.4 为什么使用 BM25 而不是 embedding？

合理回答：

- 代码中标识符、API、类型和语法 token 的精确匹配很重要；
- BM25 成本低、可解释、无需额外模型；
- 在规则类别过滤后，词法相似更有效；
- 但 BM25 对变量重命名和深层语义不敏感，可用 AST 特征、dense retrieval 或 reranker 改进。

BM25 核心思想：词频增益饱和，并通过逆文档频率提高稀有词权重，同时校正文档长度。

### 10.5 为什么结构化总结有帮助？

- C 的 I/O、数组范围、指针语义可能隐含在实现中；
- 直接翻译容易只模仿表面语法；
- 先抽象输入、输出、功能，相当于构造语义中间表示；
- 让模型先回答“程序做什么”，再回答“Rust 中如何实现”。

风险：摘要本身可能错，并将错误传给翻译。因此可增加：

- 静态分析结果校验；
- 双模型或多样采样一致性；
- 执行测试兜底；
- 将摘要作为辅助而非唯一事实源。

### 10.6 编译成功是否等于翻译正确？

不等于。

- CSR 只验证语法、类型和借用规则；
- 行为一致需要测试或形式化验证；
- `unsafe` 少也不代表逻辑正确；
- 可能生成可编译但绕开原功能的退化实现。

因此至少同时看：CA、CSR、UR/ULR，并分析失败类别。

### 10.7 数据泄漏如何控制？

公开论文从 xCodeEval 训练集构造检索库，并在评估集测试。面试时应说明：

- train/eval 按官方 split 隔离；
- 去除完全相同与近重复代码；
- 不使用评估样本的目标 Rust；
- 检索示例只能来自训练库；
- 最好进行 AST/MinHash 近重复检查。

### 10.8 IRENE 的局限

- 静态规则覆盖有限；
- BM25 语义能力弱；
- 编译器只提供句法和类型反馈；
- 多轮修复可能循环；
- Prompt 长度增加；
- 小模型可能理解不了复杂规则与示例；
- 函数级方法不能直接处理仓库级依赖。

## 11. TRAVEL：MCTS + 双奖励 GRPO

### 11.1 一句话项目定义

> 先利用 Rust 规则引导 MCTS 搜索能产生正确翻译的推理路径，再用这些路径进行 SFT 冷启动，并结合执行奖励与推理质量奖励做 GRPO，使小模型内化可靠翻译能力。

### 11.2 完整流程

```text
C 函数
  ↓
生成可验证测试输入
  ↓
运行原 C 程序得到参考输出
  ↓
规则引导 MCTS 搜索推理路径
  ↓
生成 Rust 并编译/执行
  ↓
终局奖励回传，得到路径价值
  ↓
高质量轨迹用于 SFT 冷启动
  ↓
训练推理过程奖励模型
  ↓
GRPO：执行奖励 + 推理奖励
  ↓
评测 CA / CSR / UR / ULR
```

### 11.3 MCTS 中状态、动作、奖励是什么？

- 状态 `s_t`：当前已累计的自然语言推理轨迹；
- 动作 `a_t`：生成下一步推理；
- 终止：推理完成并生成 Rust 代码，或达到最大步数；
- 奖励：编译并在验证测试上执行后的结果；
- 回传：终局奖励更新路径上节点的访问次数和价值估计。

### 11.4 PUCT 为什么能平衡探索与利用？

概念式：

```text
score = Q(s,a) + c_puct × prior(a|s) × sqrt(N_parent) / (1 + N(s,a))
```

- `Q` 高：过去结果好，倾向利用；
- prior 高：模型认为动作合理；
- 访问次数少：探索奖励更高；
- `c_puct` 控制探索强度。

### 11.5 Rust 规则如何引导 MCTS？

不是硬编码删除所有不合规则的节点，而是：

- 在 Prompt 和 few-shot 中注入规则；
- 要求推理先分析 C 语义，再选择 Rust 规则；
- 改变动作先验，使规则一致的步骤更容易被采样和扩展；
- 最终仍由编译和执行验证结果。

### 11.6 Verifiable Components 是什么？

公开论文中，对缺少测试的 C 函数：

1. 用 Qwen2.5-Coder-32B-Instruct 生成 5 个测试输入；
2. 在原 C 程序上执行；
3. 记录输入和参考输出；
4. Rust 翻译在相同输入上运行并比较输出。

这为 MCTS 和 RL 提供可执行反馈。

### 11.7 自动生成测试有什么风险？

- 只生成 5 个输入，覆盖率有限；
- 可能遗漏边界值、溢出、空指针和未定义行为；
- 生成测试的强模型可能带来偏差；
- 原 C 程序本身可能有未定义行为；
- 相同输出不一定证明所有语义等价；
- 测试分布可能与评估分布不一致。

改进：

- fuzzing、property-based testing、符号执行；
- 静态分析生成边界条件；
- 差分测试；
- 覆盖率反馈驱动测试生成；
- 对未定义行为样本过滤或单独处理。

### 11.8 PRM 与 ORM 的区别

- ORM/结果奖励：评价最终代码是否编译、测试是否通过；
- PRM/过程奖励：评价中间推理是否遵循规则、是否捕获源语义；
- ORM 客观但稀疏；
- PRM 稠密但可能存在模型偏差和 reward hacking；
- 双奖励的目标是用执行结果锚定真实性，用过程奖励改善信用分配。

### 11.9 为什么需要 SFT 冷启动？

如果初始策略几乎无法生成格式正确的推理和 Rust：

- 大量 rollout 都是相同低奖励；
- 组内 reward 方差接近 0，GRPO 无有效梯度；
- 探索空间太大；
- 训练不稳定且成本高。

SFT 先让策略进入“能生成基本正确结构”的区域，RL 再优化结果和推理质量。

### 11.10 GRPO 与 PPO 的核心区别

PPO 通常需要：

- actor policy；
- critic/value model；
- reference model；
- reward model或规则奖励。

GRPO 对同一 prompt 采样 `G` 个响应，以组内 reward 均值和标准差构造相对 advantage，从而省去单独 critic：

```text
A_i = (r_i - mean(r_1...r_G)) / std(r_1...r_G)
```

再使用 clipped policy ratio 和 KL 约束更新策略。

优势：

- 少一个 critic，降低显存与训练复杂度；
- 适合有可验证 reward 的推理任务。

局限：

- 每个 prompt 要多次采样，rollout 成本高；
- 组内奖励全相同时 advantage 消失；
- 对 reward 尺度、group size、采样温度敏感；
- 长输出的 token 归一方式会影响训练；
- reward hacking 仍然存在。

### 11.11 TRAVEL 的最终奖励

```text
r = λ_exec × r_exec + λ_reason × r_reason
```

公开设置中 `λ_exec = λ_reason = 0.5`。

执行奖励：

- 编译失败：-1；
- 编译成功但 0 个测试通过：-1；
- 否则使用测试通过率。

推理奖励由训练后的奖励模型对 `(C, P, R)` 评分。

### 11.12 为什么奖励模型采用生成式预测？

论文将 MCTS 路径价值作为目标，让模型生成对应价值 token，相当于隐式回归。

面试官可能追问：为什么不用标量回归头？

可答：

- 可直接复用因果语言模型和 SFT 基础设施；
- 不需修改模型结构；
- 便于与现有生成框架结合。

同时承认缺点：

- 连续值离散化或文本化会损失精度；
- 输出格式错误需要处理；
- 标量回归通常更直接；
- 应通过校准误差和排序相关性验证 reward model。

### 11.13 关键公开训练参数

必须熟悉但不必逐个死背：

- backbone：Qwen2.5-Coder 3B/7B、CodeGemma 7B；
- MCTS backbone：Qwen2.5-Coder-32B-Instruct；
- 最大推理步数：5；
- GRPO group size：8；
- KL 系数：0.001；
- clip epsilon：0.2；
- learning rate：`1e-6`；
- batch：32 prompts，每个 8 个响应；
- 2 epochs，最大序列 4096；
- LoRA：`r=32`、`alpha=64`、dropout 0；
- 4 张 A100。

### 11.14 为什么 RL 提升可能较小但仍有价值？

Qwen 7B 从 SFT 的 68.35% CA 到 71.07%，绝对提升 2.72 pp。评价价值时要看：

- 是否跨多个 backbone 一致；
- 是否通过消融证明 reward 和 RL 的作用；
- 提升是否集中在真正复杂的语义样本；
- 训练与推理成本；
- 是否牺牲 CSR、延迟或安全；
- 统计显著性和置信区间。

### 11.15 TRAVEL 最危险的追问

#### 问：PRM 来自 MCTS，MCTS 又使用同一类测试奖励，会不会只是学习测试偏差？

答题方向：

- 确实存在同源监督和过拟合风险；
- 训练与评估测试必须隔离；
- PRM 只能补充信用分配，不能取代独立执行验证；
- 需要跨数据集、工业集和消融验证泛化；
- 更强验证应加入 fuzzing、隐藏测试和静态属性。

#### 问：为什么不直接 Best-of-N，而要训练？

- Best-of-N 在推理时持续支付多次采样和验证成本；
- 训练能将搜索发现内化到单次生成策略；
- 但如果任务量小、验证便宜，Best-of-N 可能更经济；
- 应比较训练成本、单次推理成本和请求规模的盈亏平衡点。

#### 问：MCTS 用 32B 构数据，7B 是否只是蒸馏强模型？

- 有蒸馏成分，强模型提供动作先验和轨迹；
- 但轨迹经过编译/执行验证，不是直接模仿教师输出；
- RL 还利用在线策略采样与可验证奖励；
- 应通过“普通强模型 SFT 数据 vs MCTS 验证轨迹”消融证明搜索与验证贡献。

# 第五部分：大模型基础知识

## 12. Transformer 高频题

### 12.1 Self-Attention 公式

```text
Q = XW_Q, K = XW_K, V = XW_V
Attention(Q,K,V) = softmax(QK^T / sqrt(d_k) + mask)V
```

为什么除以 `sqrt(d_k)`：若 Q、K 各维方差稳定，点积方差随维度增大；缩放避免 softmax 过度饱和和梯度变小。

### 12.2 Causal Mask

Decoder-only 模型中，第 `t` 个 token 只能看到 `≤t` 的 token。通常在未来位置加负无穷，使 softmax 后概率为 0。

### 12.3 MHA、MQA、GQA

- MHA：每个 query head 有独立 K/V head，表达力强但 KV Cache 大；
- MQA：所有 query heads 共享一组 K/V，显存和带宽小，但可能损失质量；
- GQA：多个 query heads 共享一组 K/V，是质量与效率折中。

推理阶段 GQA 主要减少 KV Cache 和内存带宽压力。

### 12.4 Pre-Norm 与 Post-Norm

- Post-Norm：残差后做 LayerNorm，原始 Transformer 使用；
- Pre-Norm：进入子层前归一化，深层训练通常更稳定；
- 现代 LLM 常用 RMSNorm + Pre-Norm。

RMSNorm 只按均方根缩放，不减去均值，计算更简单。

### 12.5 SwiGLU

FFN 的门控形式可写为：

```text
SwiGLU(x) = SiLU(xW_gate) ⊙ (xW_up)
output = SwiGLU(x)W_down
```

门控提高非线性表达，现代 LLM 中很常见。

### 12.6 RoPE

RoPE 对 Q/K 的二维通道施加与位置相关的旋转，使点积自然包含相对位置信息。

优点：

- 无需学习绝对位置表；
- 相对位置表达自然；
- 可配合位置插值和频率缩放扩展上下文。

问题：直接外推到训练长度之外可能退化。

### 12.7 为什么训练是 `O(T²)`？

标准注意力需要构造 `T×T` 的注意力分数矩阵。长上下文同时带来：

- attention FLOPs 二次增长；
- 激活显存增加；
- 推理 KV Cache 线性增长；
- prefill 延迟显著增加。

### 12.8 FlashAttention 为什么快？

核心不是少算 attention，而是 IO-aware：

- 分块把 Q/K/V 放入片上 SRAM；
- 避免将完整 `T×T` attention matrix 写回 HBM；
- 使用在线 softmax 保持数值正确；
- 大幅减少显存读写和中间激活。

### 12.9 MoE

MoE 每个 token 只路由到少量专家：

- 总参数量大；
- 单 token 激活参数较少；
- 计算效率较高。

难点：

- 路由负载不均；
- expert capacity 与 token drop；
- all-to-all 通信；
- 专家并行部署复杂；
- 训练和推理稳定性。

## 13. Pretrain 全流程

即使没有直接做过，也应能完整描述。

### 13.1 数据流水线

```text
数据获取
→ 格式解析
→ 语言/领域识别
→ 质量过滤
→ 安全与隐私过滤
→ 精确/近似去重
→ benchmark contamination 检查
→ tokenizer 编码
→ 数据配比与 curriculum
→ packing/sharding
→ 训练与在线数据监控
```

### 13.2 去重为什么重要？

- 重复数据浪费计算；
- 高频模板扭曲分布；
- 增加记忆和隐私泄露；
- 训练/测试重复导致虚高；
- 网页镜像会产生大规模近重复。

方法：

- URL/document 精确哈希；
- n-gram MinHash + LSH；
- 代码可结合 token、AST 或规范化标识符；
- 评测污染可对 benchmark 片段做 n-gram 检索。

### 13.3 数据配比怎么做？

不能只按原始数据量采样，否则高资源语言和网页文本会支配训练。需考虑：

- 语言和领域目标；
- 数据质量；
- 模型能力短板；
- 重复率；
- 温度采样；
- curriculum；
- 小规模 ablation 或 scaling 实验。

### 13.4 Tokenizer

常见 BPE、SentencePiece/Unigram。关注：

- 多语言字符覆盖；
- 代码缩进和符号；
- 数字和特殊 token；
- 平均 token/字符比；
- 词表大小对 embedding 参数、序列长度和跨语言共享的影响。

### 13.5 训练目标

Decoder-only 主流目标是 next-token prediction：

```text
L = -Σ_t log p(x_t | x_<t)
```

### 13.6 Packing

将多个短样本拼接到固定长度，提高 token 利用率。必须正确设置：

- attention mask；
- position IDs；
- 样本边界；
- loss mask；
- 是否允许跨样本注意。

### 13.7 训练稳定性监控

- loss 与不同数据域 loss；
- gradient norm；
- learning rate；
- token throughput；
- GPU utilization；
- NaN/Inf；
- 激活和权重范数；
- 数据 shard 异常；
- checkpoint 可恢复性。

出现 loss spike 时排查：

- 异常 batch 或脏数据；
- 学习率过大；
- 混合精度溢出；
- 梯度累积/裁剪错误；
- 分布式通信或权重不同步；
- tokenizer/label shift 错位。

### 13.8 分布式训练

- DP：复制模型，切数据；
- TP：切层内矩阵，通信频繁；
- PP：按层切分，有 pipeline bubble；
- ZeRO/FSDP：切 optimizer、gradient、parameter 状态；
- CP/SP：切序列维度，适合长上下文；
- EP：MoE 专家并行。

大模型训练常组合多种并行策略。

## 14. SFT、LoRA 与偏好对齐

### 14.1 SFT

SFT 仍是 token-level cross entropy，但通常只对 assistant 输出计算 loss：

```text
L_SFT = -Σ_{t∈assistant} log πθ(y_t | x, y_<t)
```

高频问题：

- 数据质量通常比单纯数量更重要；
- 多轮对话要正确 mask system/user token；
- packing 不可造成样本泄露；
- 需要控制长度、领域和难度分布；
- 过度 SFT 可能损伤基础能力或造成风格收缩。

### 14.2 LoRA

冻结原矩阵 `W`，只训练低秩增量：

```text
W' = W + (α/r)BA
```

若 `W ∈ R^(d_out×d_in)`：

- `A ∈ R^(r×d_in)`；
- `B ∈ R^(d_out×r)`；
- 可训练参数约为 `r(d_in+d_out)`。

`r` 控制容量，`alpha` 控制缩放。LoRA 省 optimizer/gradient 显存，但基础权重和激活仍占显存。

### 14.3 PPO

核心是限制新旧策略变化过大：

```text
ratio = πθ(a|s) / πold(a|s)
Lclip = min(ratio·A, clip(ratio,1-ε,1+ε)·A)
```

LLM PPO 常涉及 actor、critic、reference、reward 四类模型或角色，成本较高。

### 14.4 GRPO

用同一 prompt 的组内相对 reward 代替 critic baseline。必须知道：

- group sampling；
- reward normalization；
- clipped ratio；
- reference KL；
- 同组全对/全错会导致学习信号弱。

### 14.5 DAPO

DAPO 针对大规模推理 RL 的典型问题引入：

1. **Clip-Higher**：放宽上侧 clip，促进低概率 token 探索；
2. **Dynamic Sampling**：过滤组内全对或全错、无有效 advantage 的 prompt；
3. **Token-Level Policy Gradient Loss**：按 token 聚合，减小响应长度带来的样本权重偏差；
4. **Overlong Reward Shaping**：对超长截断进行平滑惩罚，避免突变噪声。

### 14.6 DPO 与 RLVR

- DPO：从偏好对 `(chosen, rejected)` 直接优化，无需在线 rollout 和 reward model；
- RLVR：使用数学答案、代码测试、工具结果等可验证 reward 做在线或近在线 RL；
- DPO 简单稳定，但受静态偏好数据限制；
- RLVR 能探索新轨迹，但 rollout 成本高，验证器也可能被钻漏洞。

### 14.7 Reward Hacking

例子：

- 代码生成直接硬编码测试答案；
- Agent 重复调用容易得分的工具；
- 为获得“详细”评分生成冗长文本；
- 利用 Judge Prompt 注入；
- 逃避任务但输出符合格式。

缓解：

- 隐藏测试与动态测试；
- 多维 reward 和硬约束；
- 过程与结果交叉验证；
- adversarial evaluation；
- reward audit；
- 训练/评测验证器隔离。

# 第六部分：Agent 与 Agent-RL

## 15. Agent 基础

### 15.1 ReAct

ReAct 交替进行 reasoning 与 action：

```text
Observation → Thought → Action → Observation → ... → Answer
```

优势：工具反馈可修正推理；缺点：链路长、成本高、可能循环，显式思维文本也不一定真实反映内部推理。

### 15.2 Planning

常见策略：

- plan-and-execute；
- hierarchical planning；
- tree search；
- reflection/refinement；
- dynamic replanning。

计划不是越详细越好。环境变化时，过度固定计划反而脆弱。

### 15.3 Tool Calling

关键工程点：

- JSON Schema 与参数校验；
- 工具权限和 allowlist；
- 幂等性；
- 超时、重试与熔断；
- side effect 操作二次确认；
- 工具结果长度控制；
- Prompt injection 防护；
- 结果与执行状态可追踪。

### 15.4 Memory

- working memory：当前上下文；
- episodic memory：历史交互或成功轨迹；
- semantic memory：抽取后的稳定事实；
- procedural memory：技能、Prompt、工作流。

记忆系统必须考虑：写入条件、去重、过期、冲突、隐私、检索和可删除性。

### 15.5 RAG

标准流程：

```text
query → rewrite → retrieve → rerank → context assembly → generate → citation/verification
```

检索指标与生成指标要分开：

- Recall@K、MRR、nDCG；
- answer correctness、faithfulness、citation correctness；
- latency、token 和成本。

### 15.6 MCP

MCP 的价值是标准化模型/Agent 与工具、资源、Prompt 的连接接口，降低不同客户端与服务之间的集成成本。面试时重点讲协议分层、能力发现、权限和安全，不要只说“能调用工具”。

## 16. Agent-RL 难点

### 16.1 如何建模

Agent 通常是 POMDP：

- 状态不可完全观测；
- observation 来自用户、检索和工具；
- action 包括自然语言、工具选择和参数；
- reward 可能只在轨迹末端出现；
- 环境存在工具失败和用户变化。

### 16.2 信用分配

最终失败可能源于很早的路由或改写。可采用：

- step-level reward；
- process reward model；
- advantage 回传；
- hindsight relabeling；
- counterfactual/ablation；
- 将轨迹拆为可验证子任务。

### 16.3 多轮 rollout 的工程问题

- 环境吞吐成为瓶颈；
- 工具调用有延迟和非确定性；
- 轨迹长度差异大；
- rollout policy 与 training policy 版本不一致；
- 工具或知识库更新导致环境非平稳；
- 失败请求需要可恢复；
- 必须保存完整 trajectory 和环境版本。

### 16.4 奖励设计示例：电商客服 Agent

```text
R = w1·任务完成
  + w2·答案正确
  + w3·知识忠实
  + w4·工具参数正确
  - w5·无效步数
  - w6·延迟/成本
  - w7·安全违规
```

安全违规、越权操作等应考虑硬门控，而不只是可被其他得分抵消的软惩罚。

### 16.5 On-policy 与 Off-policy

- On-policy：用当前/近当前策略生成数据，分布匹配但 rollout 贵；
- Off-policy：复用历史轨迹，样本效率高但存在策略分布偏移；
- 轨迹回放时需要记录行为策略版本和 log probability；
- 可使用重要性采样、限制数据新鲜度或 rollout correction。

# 第七部分：推理系统与 vLLM

## 17. Prefill 与 Decode

- Prefill：并行处理输入 token，计算量大，偏 compute-bound；
- Decode：每步生成一个 token，需要读取权重和 KV Cache，常偏 memory-bandwidth-bound；
- TTFT 主要受排队和 prefill 影响；
- TPOT/ITL 主要反映 decode 速度。

## 18. KV Cache

自回归生成时缓存历史 token 的 K/V，避免每一步重新计算。

近似显存：

```text
KV bytes = 2 × layers × batch × seq_len × n_kv_heads × head_dim × bytes_per_element
```

其中 `2` 代表 K 和 V。GQA/MQA 通过减少 `n_kv_heads` 降低 KV Cache。

## 19. PagedAttention

传统连续 KV 内存会产生预留浪费和碎片。PagedAttention 借鉴虚拟内存：

- 将 KV Cache 划分为固定大小 block；
- 逻辑连续，物理可不连续；
- 按需分配；
- 多序列可共享前缀 block；
- 降低内部/外部碎片，提高可并发请求数。

## 20. Continuous Batching

静态 batching 要等待整批请求完成；continuous batching 可以：

- 已完成请求立即退出；
- 新请求动态进入；
- 每个调度步重新组织 batch；
- 提高 GPU 利用率和吞吐。

代价是调度更复杂，并需权衡吞吐、尾延迟和公平性。

## 21. 常见推理优化

- GQA/MQA；
- FlashAttention；
- continuous batching；
- prefix caching；
- speculative decoding；
- quantization；
- tensor/data/expert parallel；
- chunked prefill；
- prefill/decode disaggregation；
- KV Cache offload/compression。

## 22. Speculative Decoding

小 draft model 一次提出多个 token，大 target model 并行验证。若 draft 与 target 接近，可减少 target 串行 decode 步数；算法设计正确时不改变 target 分布。

收益取决于：

- acceptance rate；
- draft 成本；
- 验证批量；
- batch size；
- 请求长度。

## 23. 量化

- Weight-only：主要减少权重带宽与显存；
- W8A8/FP8：权重和激活同时低精度；
- KV quantization：降低长上下文 KV 占用；
- PTQ 简单但可能掉点；
- QAT 用训练适配量化误差，成本更高。

评估必须同时看：任务质量、TTFT、TPOT、吞吐、显存、不同长度和 batch。

## 24. vLLM 被追问时的回答边界

简历写了“熟悉 vLLM”，面试官可能直接问：

- PagedAttention 的 block table 如何工作？
- continuous batching 如何调度？
- `gpu_memory_utilization` 太高会怎样？
- prefix caching 什么时候收益最大？
- tensor parallel 与 pipeline parallel 如何选？
- 为什么吞吐提高但 P99 变差？
- 如何做线上 benchmark？

如果你只做过启动服务而没有改过内核，应如实说：

> 我有部署、参数调优和机制理解经验，但没有开发过 vLLM CUDA kernel。我的实际工作主要是 `[填写真实范围]`。

# 第八部分：Long Context

## 25. 长上下文的三类瓶颈

1. **计算**：标准 attention `O(T²)`；
2. **存储**：KV Cache `O(T)`；
3. **能力**：模型未必能有效检索并利用远距离信息。

## 26. 常见扩展方法

- 位置插值；
- RoPE/NTK/YaRN 类频率缩放；
- 长文本继续训练；
- sliding-window 或 sparse attention；
- chunk/recurrent memory；
- context parallel；
- RAG、层级摘要和上下文压缩。

仅修改 RoPE 参数不等于真正获得长上下文能力，还需要长数据训练和 needle、multi-hop、长文生成等评测。

## 27. 仓库级代码场景中的方案

推荐回答：

> 我不会把整个仓库直接塞入长窗口。先解析符号和依赖图，对当前迁移单元检索直接依赖、接口定义和相关测试；上层模块使用摘要，关键函数保留原文；编译报错后再按错误位置动态扩充上下文。Long Context 是承载能力，依赖建模和检索才决定有效上下文质量。

## 28. 长上下文怎么评估

- needle-in-a-haystack 只是基础；
- 多 needle 与冲突信息；
- 跨段 multi-hop；
- 长文档问答；
- 长代码依赖与编辑；
- 不同位置和长度分桶；
- 质量、TTFT、吞吐、KV 显存共同评估。

# 第九部分：多模态与多语言

## 29. VLM 基本架构

```text
图片/视频
  ↓
Vision Encoder（ViT 等）
  ↓
Projector / Resampler
  ↓
视觉 token
  ↓
与文本 token 拼接进入 LLM
  ↓
理解、生成、定位或工具调用
```

典型训练阶段：

1. 视觉-语言对齐；
2. 多模态预训练；
3. 多模态指令微调；
4. 偏好对齐或可验证 RL；
5. 特定业务微调。

## 30. CLIP 对比学习

图像编码器和文本编码器分别得到向量，使用 batch 内正负样本做双向对比学习：拉近匹配图文，推远不匹配图文。

问题：batch 内可能存在假负例；商品场景中外观相似但 SKU 不同，需要细粒度属性和 hard negative。

## 31. 动态分辨率

固定缩放会损失商品文字、规格表和局部细节。动态分辨率/切图可保留原始信息，但视觉 token 数量增加，需要：

- patch merge；
- window attention；
- token pruning/resampling；
- 分辨率与延迟预算控制。

Qwen2.5-VL 的公开技术报告强调 native dynamic resolution、Window Attention 和视频绝对时间编码。理解这些设计的“为什么”比记模型名称更重要。

## 32. 视频理解

关键问题：

- 帧采样与镜头切分；
- 时序位置编码；
- 长视频 token 爆炸；
- 音视频对齐；
- 事件定位；
- 商品展示中的关键帧、口播和字幕融合。

## 33. 语音/Omni

两种路线：

- 级联系统：ASR → LLM → TTS，模块成熟、易控制，但误差累积和延迟较高；
- 端到端多模态模型：直接处理/生成音频 token，交互自然，但训练、数据和安全控制更复杂。

## 34. Diffusion 基础

前向过程逐步加噪，反向模型学习去噪。常见训练目标是预测噪声、速度 `v` 或数据本身。

商品内容生成需重点解决：

- 商品主体与文字准确；
- 品牌和款式一致性；
- 不虚构功能；
- 多视角一致；
- 可控编辑；
- 版权与安全审核。

## 35. 多语言训练

难点：

- 高低资源语言不平衡；
- tokenizer 效率差异；
- 翻译腔与文化差异；
- 商品属性和单位本地化；
- 跨语言检索对齐；
- 不同市场政策与敏感内容。

方法：

- 温度采样和数据配比；
- 高质量平行语料；
- back translation；
- 跨语言对比学习；
- glossary/术语约束；
- language-specific 与 cross-lingual 双重评测。

# 第十部分：电商业务落地

## 36. 电商智能导购系统设计题

### 36.1 需求

用户多轮表达模糊需求，例如：

> “想买一台适合宿舍、预算 300 元以内、声音不要太大的风扇。”

系统需要澄清、检索、比较、推荐，并保证价格库存真实。

### 36.2 推荐架构

```text
用户请求
  ↓
意图/风险路由
  ↓
需求结构化与澄清
  ↓
搜索召回（关键词 + 向量 + 行为）
  ↓
商品/用户特征融合与重排
  ↓
LLM 生成比较与理由
  ↓
价格/库存/优惠工具实时校验
  ↓
安全与事实校验
  ↓
回复 + 轨迹记录 + 用户反馈
```

### 36.3 为什么不能让 LLM 直接推荐商品？

- 商品全集和实时状态不在参数中；
- 价格、库存、优惠会变化；
- 容易虚构 SKU 和属性；
- 排序需要用户行为与业务约束；
- 合规和广告规则需要硬约束。

LLM 更适合：需求理解、澄清、解释、比较和工作流编排；候选召回、库存价格和交易动作由可靠系统提供。

# 第十一部分：A/B 实验

## 41. 基本流程

```text
提出假设
→ 定义主指标与护栏指标
→ 确定随机化单元
→ 估计 MDE 与样本量
→ A/A 与埋点检查
→ 分流运行
→ SRM/数据质量检查
→ 显著性与置信区间
→ 分群和长期效应
→ 决策与复盘
```

## 42. 随机化单元

可按用户、session、query、商家等分流。选择不当会导致污染：

- 同一用户在两个策略间切换，体验不一致；
- 推荐系统中用户行为反过来影响模型；
- 商家内容实验可能影响所有看到商品的用户。

## 43. 主指标与护栏指标

智能导购示例：

- 主指标：会话转化率或加购率；
- 中间指标：推荐点击率、任务完成率；
- 护栏：P95 延迟、退款率、投诉率、幻觉率、成本。

指标必须在实验前确定，避免看到结果后挑指标。

## 44. MDE 与样本量

- MDE：业务上值得检测的最小效果；
- 样本量受基线率、方差、显著性水平、统计功效和 MDE 影响；
- MDE 越小，需要样本越多；
- 不应通过每天偷看并在显著时立即停止普通固定样本实验。

## 45. SRM

Sample Ratio Mismatch：实际组间样本比例显著偏离预设。可能由：

- 分流 bug；
- 埋点丢失；
- 过滤逻辑不同；
- 用户重复计数；
- 实验资格判定发生在分流后。

出现 SRM 时应先修数据问题，不直接解释业务结果。

## 46. CUPED

使用实验前与目标指标相关的协变量减少方差，从而提高统计功效。协变量必须是 treatment 发生前确定，不能被实验影响。

## 47. 多重检验

同时看大量指标、分群和实验会提高假阳性。处理方法：

- 预注册主要假设；
- Bonferroni/Holm；
- FDR；
- 将探索性与确认性分析分开。

## 48. 离线提升但线上下降怎么办？

排查：

- 离线数据分布与线上不同；
- 指标与用户价值不一致；
- 延迟和失败率；
- 新颖性/位置偏差；
- 模型改变用户行为；
- 评测集过拟合；
- 长期指标与短期点击冲突。

这道题应结合你的小鹏经验回答：离线回归是上线门槛，不是业务价值的最终证明。

# 第十二部分：机器学习与工程基础追问

## 49. 常见机器学习问题

### 49.1 过拟合怎么办？

- 更多且更有代表性的数据；
- 正则化、weight decay、dropout；
- early stopping；
- 数据增强；
- 降低模型容量；
- 交叉验证；
- 检查数据泄漏和评测集污染。

### 49.2 Precision、Recall、F1

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2PR / (P + R)
```

风险识别通常更关心 recall；高成本人工处理可能更关心 precision。必须结合业务代价。

### 49.3 交叉熵与 KL

```text
H(p,q) = H(p) + KL(p||q)
```

当真实分布固定时，最小化交叉熵等价于最小化 `KL(p||q)`。

### 49.4 为什么 AdamW 把 weight decay 与梯度更新解耦？

在 Adam 的自适应缩放下，将 L2 正则直接加到梯度不再等价于标准权重衰减。AdamW 对参数独立衰减，行为更清晰。

### 49.5 梯度裁剪

通常按全局范数裁剪，防止少数 batch 产生过大更新。混合精度训练时应在 unscale 后裁剪。

## 50. PyTorch/训练工程问题

需要能解释：

- `model.train()` 与 `model.eval()`；
- `torch.no_grad()`；
- gradient accumulation；
- mixed precision 与 loss scaling；
- DDP 的梯度同步；
- FSDP/ZeRO-3 的参数切分；
- gradient checkpointing 的计算换显存；
- checkpoint 保存 optimizer、scheduler、RNG 和 dataloader 状态的重要性。

## 51. Python 与算法

代码面试重点：

- `dict/set`；
- `collections.deque/defaultdict/Counter`；
- `heapq`；
- 二分、滑窗、DFS/BFS、堆、并查集、动态规划；
- 时间与空间复杂度；
- 并发、生成器、深浅拷贝。
